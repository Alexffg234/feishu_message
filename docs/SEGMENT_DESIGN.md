# 群聊话题段落重归类方案（Segment）

> 目标：把整群消息按时间流切成「在聊同一件事」的段落，解决现有依赖飞书回复链导致的归类混乱。

---

## 1. 现状与问题

现有系统把消息归类到 `conversations`（回复链），锚点是 `root_message_id`，而它取决于**飞书的显式「回复」元数据**（`parent_id` / `root_id`）。

实际群聊里大家**很少点回复按钮**，多数是直接打字接话，导致：

| 现状问题 | 表现 |
|---|---|
| 一个问题被拆散 | A 提问 → B,C,D 各自回复都成了独立 root，同属一个问题却被分成 4 段 |
| 同主题无关联 | LLM 打了相同 topic 标签，但仍是不同 conversation，没真正聚合 |
| 随机错并 | 「同人短时连发」合并逻辑，会把同一人连发的两个不同话题错并 |

**根本原因**：把「归类的锚」押在了不稳定的回复元数据上。

---

## 2. 新方案：整群话题段（Segment）

### 2.1 一句话
把群里的消息流按时间正序，切成一段段 **「连续在聊同一件事」** 的片段（segment）。一段 = 一个话题的完整讨论。

### 2.2 两个切段信号（判断边界）

**① 时间断点（硬切）**
相邻两条消息间隔 > `segment_timeout`（如 15 分钟）→ 强制切开。
> 群聊沉寂超过阈值，说明上一个话题基本结束。

**② 语义跳变（软切）**
间隔虽短，但**话题内容不相关** → 切开。
> 由 LLM 判断相邻片段是否「同一话题」，不同则切。

### 2.3 「人」作为辅助信号（不是合并依据）

人不再作为"合并/拆分"的唯一依据，而是作为**话题边界与交叉的辅助证据**：

| 场景 | 信号 | 处理 |
|---|---|---|
| 发言者连续切换 + 内容无关 | 大概率系统在聊新话题 | 辅助「软切」 |
| 同一话题被另一人打断又回来 | 交叉话题 | 标记 segment 的 `interleaved=true`，但不强行拆 |
| 同一人聚焦陈述 | 帮助 LLM 理解"这是在解释上一段" | 作为文本上下文喂给 LLM |

**核心原则**：`时间 + 内容` 是主判据，`发言者` 是辅助上下文，不单独决定归属。

### 2.4 数据模型

新增表 `message_segments`（话题段）：

| 字段 | 说明 |
|---|---|
| `id` | 段主键 |
| `chat_id` | 群 chat_id |
| `topic` | LLM 打的段主题（如"投屏问题"） |
| `start_ms` / `end_ms` | 段时间范围（毫秒） |
| `root_message_id` | 段内第一条消息（作为段锚点） |
| `message_count` | 段内消息数 |
| `participant_count` | 段内参与人数 |
| `interleaved` | 是否被其他话题穿插 |
| `created_at` / `updated_at` | 时间戳 |

`messages` 表增加 `segment_id`（BigInt，索引）。**不删除原 root_message_id / conversation_id**，新旧归类并行，便于对比与回滚。

### 2.5 实现组件

- `app/models/segment.py`：`MessageSegment` ORM
- `app/services/segment_service.py`：切段算法 + LLM 验证
- `scripts/segment_messages.py`：**离线重算脚本**（对历史全量重切，幂等）
- `app/dao/segment_repo.py`：段的读写

### 2.6 切段算法（多遍）

```
输入: 某群全部消息(时间正序)
第1遍 硬切: 按 segment_timeout 在时间断点切开 → 得到候选初段
第2遍 粗并: 每段取代表消息(首条+末条+最长), 若干段一组送给 LLM:
        LLM 判断这些相邻段是否同一话题, 同话题则合并
        (控制每次 LLM 的段数 ≤ N, 分批, 控成本)
第3遍 标记: 对最终段计算 message_count/participant_count/interleaved
写出: message_segments + 回写 messages.segment_id
```

### 2.7 增量与成本控制

- **离线全量重算**：`segment_messages.py`，对每个群跑一遍，幂等（可反复跑）。
- **LLM 调用策略**：不逐条调用，而是"一批代表消息"一次判断，N 段一批，显著降成本。
- **降级**：未配置 LLM 或调用失败 → 只用时间硬切（纯规则），仍能得到合理段落；有 LLM 时更准。

---

## 3. 相比原方案的提升

| 维度 | 原方案 | 新方案 |
|---|---|---|
| 归类锚 | 飞书回复链（不稳定） | 时间 + 话题内容 |
| 人 | 合并/拆分依据 | 辅助上下文信号 |
| 一个大问题的多条回答 | 拆散成 N 个 conversation | 归到同一个 segment |
| 纯靠回复按钮 | 强烈依赖 | 不依赖 |
| 历史重算 | 无 | 离线幂等脚本 |
