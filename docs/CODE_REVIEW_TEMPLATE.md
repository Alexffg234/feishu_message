# 变更评审模板(复制即用)

> 用法:每次发起评审时,把这个文件内容贴到 PR 描述 / 评审请求里填完即可。
> 对应 `docs/CODE_REVIEW_STANDARD.md` 第 4、5 节。

## 变更概览

- **标题**:`<type>(<scope>): <简述>`(如 `feat(topic): 新增 xx`)
- **关联提交**:`<commit hash>` / 分支 `<branch>`
- **背景与目标**:
  > 为什么做这次改动?解决什么问题?(写清上下文,评审人不需要翻聊天记录)
- **改动清单**:
  - [ ] 新增 `app/services/xxx.py` — 说明
  - [ ] 修改 `app/dao/xxx.py` — 说明
  - [ ] ...
- **影响范围**:
  - 涉及数据表/迁移:□ 是(说明) □ 否
  - 涉及外部依赖(飞书/七牛/LLM):□ 是(说明降级策略) □ 否
  - 涉及鉴权/白名单:□ 是(说明) □ 否

## 验证情况(作者自查)

- [ ] `pytest -q` 通过(改动范围相关用例列出):`<用例名>`
- [ ] 新逻辑已补测试:主路径 1 例 + 异常/降级 1 例
- [ ] LLM 相关用 fake LLM 跑通全链路(如涉及)
- [ ] 回填/归并逻辑幂等,已在本地副本验证(dry-run → apply)
- [ ] 敏感信息未入库/未进日志;新配置已同步 `.env.example` + README
- [ ] 代码通过第 6 节对应分层清单自评

## 待评审人重点关注

- [ ] 我特别想被 review 的地方:`<file>` 的 `<函数/逻辑>`(可选,帮评审人聚焦)
- [ ] 我知道的已知限制 / 后续 TODO:

---

## 评审结论

- [ ] 🔴 阻塞项(必须修):
  - _此处列评审人的 🔴 意见(留空由评审人填)_
- [ ] 🟡 建议项(本次或 backlog):
  - _由评审人填_
- [ ] 💭 吹毛求疵(可不改):
  - _由评审人填_

**最终**: □ APPROVE(可合并)  □ REQUEST CHANGES(有阻塞)  □ COMMENT(仅讨论)
