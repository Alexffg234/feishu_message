# 代码审查标准与流程

> 适用范围:飞书群聊消息采集系统(FastAPI + SQLAlchemy + pytest + GitHub/Git)。
> 目标:在「正确性 / 安全性 / 可维护性 / 性能」四个维度上拉齐代码质量,"让每一次合入都经得起推敲",同时**通过评审教会人,而不是只判对错**。

---

## 1. 目标与原则

1. **评审是门禁,不是摆设**——任何代码改动在合入 `main` 前都必须经过至少一次人工评审。
2. **先讲为什么,再讲怎么做**——每条意见说明影响和风险,给可选方案,不命令式改法。
3. **分层关注、远近有别**——DAO/服务层重逻辑与一致性,API 层重输入输出与鉴权,前端重体验与可访问性。
4. **评审是持续的,不是一次性**——同一个 PR 一轮给全,不挤牙膏式逐条补充。
5. **尊重既有约定**——本项目已统一:Conventional Commits(`feat/fix/refactor/docs/...`)、中文注释、4 空格缩进、类型标注、分层目录。新代码必须延续这些约定。

---

## 2. 适用范围与触发条件

以下变更**必须**走评审(哪怕只改一行):

| 变更类型 | 例子 |
|---|---|
| 功能新增 | 新接口、新服务、新脚本、新后台任务 |
| 缺陷修复 | bugfix、行为修正 |
| 重构 | 分层调整、dao 返回类型改动、命名统一 |
| 数据链路改动 | 表结构、索引、回填脚本、幂等逻辑 |
| 安全相关 | 鉴权、脱敏、密钥、cookie、输入校验 |
| 部署/配置 | `deploy/*`、`config.py`、`.env.example`、依赖增减 |

> 注意:`main` 分支历史中存在少量未经评审直接合入的"存量数据修正/直接改库"操作。从本流程生效起,**这类操作也必须留痕**——要么走评审,要么用脚本落地并写清 `docs/` 变更记录(见 README「变更历史」),禁止裸改生产库不留痕。

**不强制评审**的例外:仅注释、文档、`.gitignore`、README 变更,可快速走合并(但建议仍让协作者扫一眼)。

---

## 3. 角色与职责

| 角色 | 职责 |
|---|---|
| **作者(Author)** | 写代码、跑通测试、自评一遍(对照第 6 节清单)、写清 commit message、发起评审、回应意见 |
| **评审人(Reviewer)** | 对照本标准第 6~10 节逐条检查,输出带优先级的意见,最终把关是否可以合并 |
| **复核/门禁(Approver)** | 收敛分歧;确认 🔴 级问题已解决;放行合并。可与评审人同一人,但**建议作者≠评审人** |

**建议协作方式(与项目现状匹配):**
- 单人为主的项目至少引入**一个旁观评审人**跑"我能不能 5 分钟看懂?"
- 重大改动(数据链路、安全、重构)要求评审人**本地实际跑一遍验证**,而不是只看 diff。

---

## 4. 审查流程(生命周期)

```
 [作者的本地工作区]
   └─ 自评过关(第 6 节自查 + 测试通过)
        │
        └─> 提交 commit(Conventional Commits)
             │
             └─> git push 到远端分支 / 或 zip 打包交给用户
                  │
                  └─> 发起评审(描述:问题背景 / 改动内容 / 验证方式)
                       │
                       ├─ 评审人审查 diff ──> 有意见 ──> 作者修改 → 重新评审(循环)
                       │                           │
                       │                           └→ 无 🔴 阻塞项
                       ▼
                   Approver 放行
                       │
                       └─> 合并到 main
                            │
                            └─> 部署(用户执行 deploy/update.sh) + 部署后验证
```

**评审的三个明确信号:**
- `REQUEST CHANGES`(有 🔴 阻塞项,必须修)
- `APPROVE`(可合并;🟡 可留到后续迭代,记入 backlog)
- `COMMENT`(仅提问/讨论,不阻塞)

---

## 5. 每次合入必须满足的「Definition of Done」

一条改动只有**全部**满足才算"可合并":

- [ ] `pytest` 全量通过(至少在改动涉及范围),且为**新逻辑补充了测试**
- [ ] 新功能/修复**覆盖了主路径 + 至少一条边界/异常降级路径**(见第 10 节)
- [ ] 无 🔴 阻塞项;🟡 项有明确归属(`本次一起修` 或 `记入 TODO/backlog`)
- [ ] 敏感信息(密钥、明文密码、连接串)未入库;日志不打印敏感数据(见第 7 节)
- [ ] 改动可**回滚 / 幂等**(尤其回填脚本、归并类脚本)
- [ ] commit message 符合 Conventional Commits 且描述清楚"为什么"
- [ ] 文档(README 变更历史 / 相应 docs 设计)已同步

---

## 6. 分层检查清单

> 评审时逐层对照;标 `★` 的是本项目**已踩过坑**的高风险点,必须重点看。

### 6.1 通用(Python 全层)

- [ ] 命名清晰、含义唯一;方法不与实例属性同名(`def _client` vs `self._client`)
- [ ] 类型标注齐全;`from __future__ import annotations` 用于延后求值
- [ ] 公共函数有 docstring(说明用途、参数、返回、异常)
- [ ] 异常处理:只捕获预期异常;**外部依赖调用失败必须优雅降级,不抛穿中断入库**(见 6.5)
- [ ] 无显式 `# noqa` 硬塞;无死代码/无用 import
- [ ] 时间、金额等不裸加不加单位;配置经 `config.py` 统一读取,不散落魔法数字

### 6.2 API 层 `app/api/`

- [ ] 路由与 `app/main.py` 的**鉴权中间件/白名单**一致:
  - 页面未登录 → 302 跳登录;接口未登录 → 401;`/feishu/event`、`/static/**` 等白名单正确放行
- [ ] 输入有校验(Pydantic schema / 参数校验),不信任客户端
- [ ] 返回结构统一、错误码与状态码合理;不向客户端泄露内部堆栈/DB 明细
- [ ] 新增 `/health*` 之外的探活不随意放行鉴权

### 6.3 DAO 层 `app/dao/` ★

- [ ] ★ **返回类型**统一约定:给路由/序列化用返回**纯 dict**(不能返回裸 ORM,否则 FastAPI JSON 序列化 500)
- [ ] ★ 改 dao 返回类型(dict/ORM)时,必须排查**所有下游消费者**(不止路由,还有 summary_service 等按 `.attr` 访问的地方)
- [ ] ★ 统计类查询要先 `session.flush()` 再 count,否则读到旧值 0
- [ ] 批量操作注意事务边界;回填/归并类逻辑**幂等**,可重复执行
- [ ] 查询避免 N+1(见第 8 节);合理索引支撑常用 WHERE/排序

### 6.4 Models 层 `app/models/`

- [ ] 表字段、类型、可空性、默认值定义合理
- [ ] 常用查询字段有索引 / 唯一约束;无遗漏外键关系
- [ ] 新增表/加列有配套 `scripts/*.py` 迁移或 `init_db.py` 幂等补齐
- [ ] 枚举/状态用有意义的常量,不用裸字符串

### 6.5 Services 层 `app/services/` ★

业务逻辑核心,风险最高,逐项重点看:

- [ ] ★ **外部依赖(飞书 / 七牛 / LLM)失败必须降级**,返回空串/占位,绝不因依赖异常中断入库
  - 示例范式(本项目):`ImageService` 无凭据/失败返回空 `image_url`;`UserNameService` 失败返回 open_id 不崩
- [ ] ★ UI 调用的 LLM 延迟 import,本地没装依赖也不崩
- [ ] ★ LLM 打标/缝合等**本地验证不能只靠"禁用"路径**——禁用成功会掩盖启用路径的 bug;评审要求用 fake LLM 跑通全链路
- [ ] 后台线程(会话缝合/主题总结)注意**多 worker 互斥**(`SchedulerLock` 租约),防重复执行
- [ ] 归并/缝合/拆分类逻辑:护栏是否齐全?合并后是否重算统计?是否写了 `mark_block_start`

### 6.6 前端 `app/static/`

- [ ] 设计令牌唯一来源 `components.css :root`;**页面不重复定义 `:root`**,只写专属布局
- [ ] 颜色/圆角/动效取自令牌;**深色主题下文字可读、主色用提亮值**
- [ ] 语义化 + ARIA + 键盘可访问;JS 不污染全局(模块/IIFE 包裹)
- [ ] 增改版本号 `?v=x.y.z` 以便强刷缓存
- [ ] 防止 XSS:渲染用户消息用转义/文本节点,不直接 `innerHTML` 拼接不可信内容(见第 7 节)

### 6.7 脚本 `scripts/`

- [ ] 脚本带 `--dry-run` / `--apply` 两态,默认预览不写库,重要脚本加本地副本导入验证(如 `export_chat.py --out` + 副本上执行)
- [ ] 幂等可重复执行;对存量数据安全(不误删/不破坏已有还原点)
- [ ] 服务器运行用 `./.venv/bin/python`(系统 python 是 conda base,无项目依赖)

### 6.8 部署 `deploy/` 与配置

- [ ] `deploy/update.sh` 改动后跑 `--dry-run` 自测;生成 `.deps*` 类缓存文件需同步加 `.gitignore`
- [ ] `config.py` 新增配置必须同步 `.env.example` + README
- [ ] 新增依赖合理、有版本约束;不加不必要的重量级依赖

---

## 7. 安全专项(评审必须扫)

- [ ] **密钥**:`SESSION_SECRET`、`.env`、`data/.session_secret` 不入库、不进日志/告警
- [ ] **日志脱敏**:DB 连接串、token、密码等输出前必须 `mask_*`(参考 `mask_db_url`)
- [ ] **密码**:只用摘要(`pbkdf2_hmac` 加盐),不存明文;改密/注册复用统一规则
- [ ] **XSS**:前端渲染消息用转义;不要把用户可控内容直接拼进 HTML/`innerHTML`
- [ ] **SQL 注入**:SQLAlchemy 参数化查询,不用字符串拼接 SQL;review 里拼 SQL 一律 🔴
- [ ] **回调校验**:飞书事件签名/校验正确;回调不可被伪造写入
- [ ] **权限**:新增接口/路径是否该受鉴权?白名单是否过宽(除非确须放行如 `/feishu/event`)

---

## 8. 性能专项

- [ ] **N+1 查询**:循环里逐条查库是常见反模式(如循环里查用户、查标签),应批量/预加载
- [ ] 列表/树接口避免一次性加载超大集合;有 limit/分页
- [ ] 后台任务有频率/水位线控制(如会话缝合只处理水位线变化的群),避免无谓 LLM 调用
- [ ] 图片/文件资源:入库即下载上传(幂等去重 key),不依赖过期临时凭证

---

## 9. 可观测性与告警

- [ ] 新增关键路径有日志(含 message_id / chat_id 便于追链),但**不含敏感字段**
- [ ] 健康检查 `/healthz` 覆盖新引入的依赖/数据新鲜度
- [ ] 死信队列、事件队列积压有监控;新异常路径不会静默吞掉

---

## 10. 测试与验证要求

- [ ] 用 pytest,沿用 `tests/` 现有组织;每个新功能至少:
  - 主路径 1 例
  - 边界/异常降级 1 例(依赖失败、空数据、重复执行、悬挂边等)
- [ ] **LLM 相关单元用 fake LLM**(实现 `.chat()`)跑通启用路径
- [ ] 数据链路/归并改动:用本地副本(sqlite 导出)验证,再上真实库
- [ ] 评审人如改行为,需复跑受影响测试,不能只口头确认

---

## 11. 评审意见规范

每条意见统一带**优先级 + 定位 + 为什么 + 建议**:

| 标记 | 含义 | 处理 |
|---|---|---|
| 🔴 **阻塞(必须修)** | 安全漏洞、数据损坏/丢失、竞态/死锁、接口契约破坏、关键路径缺错误处理 | 合入前解决 |
| 🟡 **建议(应该修)** | 输入校验缺失、命名混乱、缺测试、N+1 性能、重复代码当抽取 | 本次或记入 backlog |
| 💭 **吹毛求疵** | 风格、小命名、文档补充、备选思路 | 可不改 |

**示例格式:**
```
🔴 Security: SQL 注入
line 42:`name` 被字符串拼接进查询。

为什么:攻击者可传 `'; DROP TABLE users;--` 注入。
建议:改用 SQLAlchemy 参数化:db.query(...).filter_by(name=name)。
```

**表达规范:** 具体、给证据(行号/堆栈/复现)、给可选方案、先肯定亮点再谈问题、不针对个人。

## 12. CI / 自动化建议(可选,渐进落地)

当前无 CI。以下从轻到重,按成本递增:

- [ ] **P0(最优先,零依赖)**:commit 前跑 `pytest -q`(本地钩子或约定)
- [ ] **P1**:GitHub Actions 在 push/PR 上跑 `pytest` + `ruff check` + 基础语法
- [ ] **P2**:补充 `ruff format --check` 统一格式
- [ ] **P3(远期)**:PR 模板(自动带 Definition of Done 勾选)、Reviewer 强制、分支保护(禁止直接 push main)

> 提示:本项目**禁止自动 push**(约定),CI 需要用户手动推送远端的环节触发;落地 CI 时不违反该约定即可。

## 附录 A:本项目高频坑位(评审重点提示)

> 来自项目实际演进中踩过的坑,review 时优先扫。

1. **dao 返回裸 ORM → FastAPI 500**:树节点必须返回 dict 且带 `mentions` 字段;改返回类型要查所有下游 `.attr` 访问。
2. **统计忘记 flush**:`update_group_stats` 先 `flush()` 再统计,否则读到 0。
3. **飞书资源下载**:必须 `GET /im/v1/messages/{message_id}/resources/{file_key}?type=image|file`,**不要**用 `/im/v1/images/{image_key}`(用户图会 234001)。
4. **发送人姓名**:库里只存 open_id,展示靠 `UserNameService` 惰性反查 + `user_names` 缓存;失败降级返回 open_id。
5. **LLM 本地验证**:禁用路径的成功会掩盖启用路径 bug——务必用 fake LLM 跑全链路。
6. **优雅降级**:飞书/七牛/LLM 任一失败,消息仍须成功入库。
7. **回填/归并幂等 + 本地副本先验**:生产库不裸改。
8. **服务器 python 用 `./.venv/bin/python`**,勿用系统 conda base。
