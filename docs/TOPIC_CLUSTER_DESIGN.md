# 群聊复杂对话「按主题归类整理」算法设计

> 目标：把一段复杂群聊消息流（多线程交织、回复链断裂、口语化短消息、图片/文件夹杂）
> 自动归整为「若干主题簇」，每个主题簇 = 一个稳定话题及其全部相关消息，可读、可检索、可统计。
>
> 本文档是设计文档：先分析对话特点（决定算法走向），再给出分层归类算法（可落地），
> 最后说明与现有 `segment_service`（切段） / `topic_service`（打标签）的衔接与实现路径。

---

## 1. 为什么"按主题归类"难：对话特点分析

先看清群聊消息的本质，再决定算法怎么设计。

### 1.1 最核心的难点：多线程话题交织（interleaving）

真实群聊里，**同一时间段往往同时在聊多个话题**：

```
09:31  A: 投屏又失败了，你们看下
09:32  B: 我早上也遇到了  → 话题1（投屏）
09:32  A: 好像设备颠倒了
09:33  C: 下午开会要发个通知   → 话题2（会议）
09:34  B: 重启一下试试
09:35  A: 好了  → 话题1 又回来
```

消息在时间流上是**线性**的，但**语义上是多线程**的。任何"按时间把流切成连续段"的做法，都会把交织的话题切进同一个段里——这正是现有"整群切段（方案Y）"的天然局限。

> **推论 1**：主题归类不能只做"时间分段"，必须再加一层**跨段的语义聚合**，
> 允许"在时间上不连续但语义相同"的消息归到同一个主题簇。

### 1.2 回复链不可靠（不能依赖显式回复关系）

飞书消息的 `parent_message_id` / `root_message_id` 来自用户**显式点"回复"按钮**。
实际群聊里大家绝大多数是**直接打字接话**，不点回复，导致：

- 同一问题的多条回复各自成为独立 root，互相无关联；
- 已有方案（conversation 按回复链聚合）因此归类混乱。

> **推论 2**：归类的主信号必须来自**内容语义 + 时间邻近**，回复链只能作为**辅助/加分**信号
> （有显式回复 = 强相关性证据；没有也不影响）。

### 1.3 大量无实义短消息（口语化、情绪化、确认语）

"收到""好的""嗯""1""ok""👍""没问题"这类消息数量多、几乎无主题信息，
但它们**在时间上属于某个话题的回应节点**，直接丢弃会丢上下文，保留则污染主题判断。

> **推论 3**：需要一层**降噪过滤**——无实义消息不参与主题判定，但作为"参与证据/热度"
> 保留在其所属时间段内。

### 1.4 短消息语义稀疏 + 非文本消息携带主题线索

- 大量消息是几个字（"这个呢？""可以""不行"），单独看没有主题信息，必须结合上下文；
- 图片、文件、视频消息没有文本，但 `file_name`、`@提及`、出现位置强化了主题线索。

> **推论 4**：主题判定应基于**段级聚合文本**（多句话合成一句话义），而不是单条短消息；
> 非文本消息的元数据（文件名、@谁）要量化成特征纳入。

### 1.5 时间热寂特性（活跃段 vs 沉寂段）

群聊在时间上呈"活跃-沉寂"交替：沉寂期打断话题，活跃期多话题并发。
已有探查数据支持这一点：间隔 P50=24s / P95=703s / P99=2167s（105 条样本）。

> **推论 5**：时间仍是有用的硬边界（跨沉寂基本是新话题），但活跃期内必须用语义细分。

### 1.6 话题漂移与子话题演化

一个话题会中途引申出新子话题（"投屏失败" → "设备型号" → "新固件升级"），
语义逐渐偏移。若聚类过严，会切碎；过松，会混入无关。

> **推论 6**：聚类要支持"簇"随消息演化（增量式），并保留"簇主话题 + 子主题"两层，容错漂移。

## 2. 算法总览：五层管线

```
输入: 某群全部消息(时间正序, 含 type/text/ts/sender/parent/root/file_name/@提及)
│
├─ L1 降噪预处理 — 过滤无实义消息, 归一化非文本/emoji/@/URL 为占位特征
├─ L2 时间切段   — 复用 segment_service(600s硬切 + LLM语义软切), 产出候选"语义片段"
├─ L3 段主题提取 — 每段聚合代表消息, LLM 得到一句话主题 + 关键词
├─ L4 主题聚类   — 特征相似度 + LLM兜底, 把相近段聚成"主题簇"(增量式, 允许时间不连续)
└─ L5 汇总整理   — 处理 interleaved 穿插归属, 输出主题簇(话题/子题/条数/人数/时间/代表消息)
```

核心创新点：**L4 主题聚类是"跨段、跨时间"的语义聚合**，补上了现有"切段 + 回复链打标"缺失的
"把分散的同类讨论归到一起"这关键一环。

## 3. 各层详细设计

### 3.1 L1 降噪预处理（规则，零成本）

**无实义消息判定**（命中即标记 `noise=true`，从主题特征中剔除）：
- 长度 ≤ 4 且命中停用词表：`收到,好的,可以,知道,嗯,好,ok,Ok,1,ok,行,是的,没问题,了解,谢谢`
- 纯 emoji / 纯符号 / "@某人" 占位
- 与上一条文本完全相同（刷屏/复读）

**归一化特征化**（给 L4 用）：
- 图片 → `[图片]`、文件 → `[文件:扩展名]`、视频/语音 → `[视频]/[语音]`
- 去掉 URL / @占位，替换为 `[链接]` / `[@名字]`
- 中英文统一小写、去标点

> 降噪后，真正参与主题判定的消息往往只剩 60%~75%（短确认语占 1/4~1/3）。

### 3.2 L2 时间切段（复用 `SegmentService`）

沿用方案Y：600s 硬切 + LLM 语义软切，产出候选段（每段是一个"在聊一件事"的时间片）。
每段保留 `interleaved` 标记（段内发言者是否交叉）。

**说明**：此层切出的是**时间连续**的语义块，是 L3/L4 的输入单元，不是最终主题。
它是"粗粒度中间产物"，最终主题在 L4 收敛。

### 3.3 L3 段主题提取（LLM，段粒度）

对每段，取代表性消息（首条 + 末条 + 最长文本 + 非文本元数据），构造：

```
[09:31] A: 投屏又失败了，你们看下
[09:32] B: 重启一下试试
[09:35] A: 好了
→ LLM: {"主题": "投屏失败排查", "关键词": ["投屏","重启","失败"]}
```

- **锚点是"段"**而非"回复链"（区别于现有 topic_service），因为段 = 语义完整单位；
- 输出结构化 `{主题, 关键词[]}`（比现有只输出字串标签信息更丰富，供 L4 聚类用）；
- 已有主题簇主标签列表回传，保证同义沿用同一措辞（复用什么）。

成本：1 段 1 次 LLM。105 条→约 8 段（真实 dry-run 结果），成本可控。

### 3.4 L4 主题聚类（核心层，分两个子步）

**L4a 特征化（轻量，零 LLM 成本）**：
- 对每段，用其**清洗后全文**构造特征向量；
- 中文特征：2-gram 字串 + 关键词（LLM 在 L3 已给），构造 `set<string>`；
- 可选升级：接入 embedding（如 text-embedding），显著提升语义召回，成本可控（按段数）。

**L4b 增量聚类（流式）**：
维护一个有序的**主题簇列表** `clusters`，逐段处理，符合"消息随时到达、增量整理"的现实：

```
for 段 in 候选段:
    sims = [ 余弦/Jaccard(段特征, 簇特征) for 簇 in clusters ]
    best, best_score = argmax(sims)
    if best_score >= 阈值_高(如0.55):        # 强相似 → 并入该簇
        簇.add(段); 簇.更新主话题/子话题; 刷新簇代表消息
    elif 阈值_低 <= best_score < 阈值_高:     # 模糊 → LLM 兜底判定
        同主题 = LLM(段摘要, 簇主话题)
        簇.add(段) if 同主题 else 新建簇
    else:                                    # 明显无关 → 新建簇
        新建主题簇
```

**跨时间合并**：簇内部消息允许时间不连续（解决 1.1 交织）。
合并的可信度 = 语义相似度为主，时间邻近为加分（回看窗口内更高分）。

**标签统一**：新段并入簇时沿用簇主标签；若 LLM 判定为"延伸子话题"，记为簇的子主题。

**L4 复杂度**：段数 N（约个位数到几十），每段与已有簇比对，O(N²) 以内，规模极小，无需复杂聚类算法；
文档同时给出规模大时的升级（HDBSCAN / 图连通分量）作为远期备选。

### 3.5 L5 汇总整理（输出 + 穿插处理）

对每个主题簇输出：
```
{
  "topic": "投屏失败排查",
  "sub_topics": ["固件升级", "重启方案"],
  "message_count": 12,
  "participants": ["A","B","C"],
  "start_time": "...", "end_time": "...",
  "interleaved": true,
  "repr": "投屏又失败了...好了",
  "messages": [ (按时间正序, 含噪声但仍完整展示) ]
}
```

**穿插（interleaved）归属策略**：
- 簇内消息按其真实时间排序展示（保持原对话节奏）、
- 但同一时间段内若确有别的主题簇，页面以"主题分栏 + 统一时间轴"呈现，
  让"同时聊两个话题"可读（跨主题不物理拆散用户聊天，而是并排展示）。

**全局排序**：主题簇按"消息数 × 时间衰减"排序（热度），或按最后活跃时间排序。

## 4. 信号权重总表

| 信号 | 用途 | 权重倾向 |
|---|---|---|
| 文本语义相似度 | L4 主判据 | ★★★（核心） |
| 时间邻近 | L2 切段 + L4 加分 | ★★ |
| LLM 语义判定 | L3 提取 + L4 模糊兜底 | ★★（精度兜底） |
| 关键词重合 | L4 特征 | ★★ |
| 显式回复链 | L4 加分 | ★（有则强相关） |
| 发言者交叉 | L2 interleaved 标记 | ★（辅助，不唯一） |
| 非文本元数据 | L3/L4 特征 | ★ |

## 5. 与现有代码的衔接与实现路径

现有组件 | 复用方式 | 新增
---|---|---
`SegmentService.segment_chat()` | L2 切段直接复用 | —
`TopicService`（LLM 打标思路） | L3 借鉴，改传"段"而非"回复链" | `L1 降噪` `L3 段级提取`
`Message` / `SegmentRepo` | 读取段与段内消息 | `L4 聚类层`
— | — | **`app/services/cluster_service.py`**（主题聚类核心）
— | — | **`scripts/cluster_topics.py`**（离线重算，幂等，`--chat/--dry-run`）
— | — | **新表 `topic_clusters`**（簇主话题/子话题/段集）或先内存返回

**落地顺序（建议）**：
1. 先写 L1+L3+L4 的**离线脚本**（`cluster_topics.py --dry-run`），在服务器 100+ 条真实数据上
   跑通、人工校验主题簇是否合理；
2. 合理后写库（新增 `topic_clusters` + `messages.cluster_id` 回写），
3. 再在 `/habits` 可视化页或新页面展示"主题簇"视图。

**评估方法**（无人工标注时的近似）：
- 同一回复链的消息 90% 落同一簇（保底不裂）；
- 簇内消息时间跨度合理（不把跨天无关并一起）；
- 簇数量 ≈ 人工可读水平（10~20 个簇对 100+ 条消息合理），不碎片化也不过度合并。

## 6. 成本与降级

- **LLM**：只用于 L3（段提取，1次/段）+ L4 模糊判定（少量）→ 100 条消息约 10~15 次调用；
- **降级**：未配 LLM → 用"关键词 2-gram Jaccard"纯规则聚类，仍能工作（L3 无关键词时
  用段内高频词兜底）；可配 embedding 提升语义召回；
- **增量**：簇按段增量维护，新消息到来自动入簇，无需全量重跑。

---

## 7. 一句话总结

> 在"切段（L2）+ 段级打标（L3）"之上，核心新增 **L4 跨段时间的语义聚类**，
> 把被多线程交织/回复链断裂打散的同类讨论重新聚合为**主题簇**，
> 再以"主题分栏 + 统一时间轴"可视化呈现，即完成"复杂对话按主题归类整理"。
