# "话题信息收录完整性"优化方案

> 目标：保证「一个话题的**所有**相关信息都被收录到同一主题簇」——
> 不只聚类分得对，还要**不漏**、**不散**。
>
> 本文档承接 `docs/TOPIC_CLUSTER_DESIGN.md`（聚类算法设计），聚焦
> 「信息会不会漏收 / 会不会被错误拆散」这一层，并给出可落地的补强方案。
> 配套代码见 `app/services/cluster_service.py` 的「收录完整性」改造。

---

## 0. 什么叫"收录完整"？

一个话题簇，除了"主题分对"，还要满足：

1. **相关消息都在**：该话题的所有消息（含"收到/好的"这类回应节点）都在簇内；
2. **证据不丢**：图片/文件/视频等非文本消息及其元数据（文件名）成为话题证据；
3. **不被人为拆散**：显式回复的问答对、回复串，不被内容相似度误拆到不同簇；
4. **碎片不孤立**：不带关键词但有承接语义的短消息，能归到所属话题而非自成一簇。

---

## 1. 当前会导致"漏收 / 拆散"的现象

基于 `cluster_chat` 现在的实现（消息级流式聚类），逐个排查：

### 现象 A：降噪把"回应节点"整个丢掉（最大的漏收源）
`_weights` 里 `_is_noise()` 命中的消息（收到/好的/嗯/👍……）被 `continue` 跳过，
`cluster_chat` 里 `if not w: continue` 又跳过一次。
结果：**这些消息既不在簇的 `messages` 里，也不计 `message_count`**。

设计文档（推论 3）明确说：无实义消息"作为参与证据/热度保留在其所属时间段内"，
但当前实现并没有真正保留——这是"话题信息收录不全"最直接的来源。
> 例：A 发"明天 10 点开会"，B/C/D 各回"收到"。若这 3 条"收到"被丢弃，
> 该会议话题的"有多少人确认了"这一关键信息就没了。

### 现象 B：非文本消息（图片/文件/视频）孤立成碎片
`_weights` 只给图片 `[图片]`、文件 `[file]` 占位符号，没有文本可聚类，
几乎必然自成一簇或在簇间漂移。
但图片/文件往往是话题的关键证据（如"投屏驱动.zip""会议纪要.png"），
其 `file_name`/上下文却成了孤立碎片或被丢掉。→ 话题证据收录不全。

### 现象 C：显式回复链没当强信号用
模型有 `parent_message_id` / `root_message_id`（用户显式点"回复"），
是"强同话题证据"。当前聚类完全没用它——
A 问、B 显式回复，两者即便内容相似度低，也可能被拆到不同簇。→ 问答对被拆散。

### 现象 D：无关键词的短消息碎片化
`_SHORT_REPLY_MAX_CHARS=6` 只对"非常短"的接话做了就近挂靠。
8~12 字、不带关键词但有承接语义的消息（"这个对投影仪有用吗"）可能因
内容相似度 < 阈值而自成一簇，分成话题碎片。→ 话题信息分散。

### 现象 E：时间硬切边界
600s 硬切把跨沉寂的同一话题切成两段（如隔夜继续讨论同问题）。
这是时间边界的取舍，属于预期内的"粗切"，不作为本方案重点（改小/软化会引入
跨话题误并，得不偿失），但可列为一个可配置开关。

## 2. 优化方案（按"收益/成本"从高到低）

### 方案 1：噪声消息"就近挂靠"（治 A，收益最大）
- **改法**：不再把噪声消息当作"不入簇"。每条噪声消息按其**时间位置**，
  挂靠到"当前在聊 / 时间最近的非噪声簇"，作为该簇的**参与节点**：
  - 计入 `message_count`，保留在 `messages` 里（展示完整对话节奏）；
  - 标记 `is_filler=true`（参与证据 / 热度，不算"主题发言"）；
  - **不参与聚类特征、不污染主题词、不算独立簇**。
- **挂靠规则**：取整群按时间正序处理时"最近一个活跃簇"；若超过一定时间窗
  （如 `_FILLER_WINDOW_SEC=1200s`）没有活跃簇，则丢弃（时间上无归属）。
- **收益**：一个话题"收到/好的/了解/👍"等所有回应全部收进来，
  主题完整性显著提升，且零污染。

### 方案 2：显式回复链作强并入信号（治 C，低成本高保真）
- **改法**：若某消息的 `parent_message_id` 或 `root_message_id` 指向
  **已在某簇里的消息**，则**直接并入该簇**（回复 = 强同话题证据），
  无需再靠内容相似度判断；找不到对应簇时才退回内容聚类。
- **收益**：A 问 B 答的问答对、整条回复串，永远不会被内容相似度拆散。
- 注意：回复消息自身的文本仍纳入该簇质心，帮助聚类更稳。

### 方案 3：非文本消息挂靠 + 元数据入证据（治 B）
- **改法**：
  - 图片/文件/视频消息并入"时间最近的非噪声簇"（同方案 1 的挂靠逻辑），
    作为该簇的非文本证据，计入 message_count；
  - 从 `raw` 提取 `file_name`/`file_key`/`mime_type`，塞进每个簇的
    **`evidence`（证据文件列表）**，并在 `repr`/页面展示，使话题证据不丢。
- **收益**：资料型消息成为话题证据而非孤立碎片。

### 方案 4：短消息承接挂靠放宽（治 D，可选）
- 把无关键词短消息的挂靠从"≤6 字"放宽为"≤N 字且紧邻活跃簇时段内"
  （N 可配，如 12），减少碎片；代价是可能把个别无关短消息归入上一话题，
  靠 LLM 兜底校正。默认保持保守（6 字），按需放宽。

### 方案 5：时间边界可配置（治 E，可选）
- `timeout_sec` 可配；后续可在页面提供"合并模式：严格(600s)/宽松(1800s)"。

## 3. 数据契约（改造后簇对象新增/变更字段）

```jsonc
{
  "topic": "投屏故障排查",
  "start_topic": "投屏又失败了",
  "message_count": 18,          // 含挂靠的噪声/非文本参与节点
  "content_count": 9,           // 真正有文本内容的主题发言数(新增)
  "participant_count": 4,
  "interleaved": true,
  "filler_count": 5,            // 其中噪声回应节点(新增)
  "evidence": [                 // 非文本证据文件(新增)
    {"type": "file", "file_name": "投屏驱动.zip", "mime_type": "application/zip"}
  ],
  "repr": ["投屏又失败了...", "投屏重启一下试试", "好了"],
  "messages": [
    {"time": "...", "sender": "...", "type": "text", "text": "...", "is_filler": false}
  ]
}
```

- 新增：`content_count`、`filler_count`、`evidence`、消息级 `is_filler`。
- 保持：`topic / message_count / participant_count / interleaved / repr / messages` 语义不变
  （`message_count` 从"纯文本主题发言"变为"含参与节点"，更贴合"话题完整信息量"）。

## 4. 落地优先级建议

| 优先级 | 方案 | 解决 | 成本 |
|---|---|---|---|
| P0 | 1 噪声就近挂靠 | 回应节点漏收 | 低 |
| P0 | 2 回复链强并入 | 问答对/回复串拆散 | 低 |
| P1 | 3 非文本挂靠 + 证据 | 资料证据孤立/丢失 | 中 |
| P2 | 4 短消息承接放宽 | 碎片化 | 中(需按数据调) |
| P3 | 5 时间边界可配 | 硬切边界 | 低 |

> 本实现优先落地 P0（方案 1 + 2）与方案 3 的核心挂靠，
> 使"一个话题的所有信息收录到"在常见群聊场景下成立；
> 方案 4/5 作为可配置项保留文档与接口。

---

## 5. 与既有能力的关系

- **不改变** `segment_by_time` 的时间硬切（复用现状）。
- **兼容** `cluster_chat(chat_id, llm)` 的调用签名（`scripts/cluster_topics.py` 无需改动）。
- **不影响** `/habits`（对话习惯分析）——那是另一个只读服务。
- **回写**：若后续落库，把 `messages.cluster_id` + `is_filler` 一并回写即可接入页面。
